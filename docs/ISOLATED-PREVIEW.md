# Experimental build and preview pipeline

## Current status

The complete model-to-container-to-browser path has now been exercised on this laptop. Docker Desktop and Ubuntu WSL2 are installed; the native Windows CLI is discovered from the per-user Desktop installation even when PowerShell PATH lacks Docker. `npm run validate:autonomous` passed for Butterfly Garden (11 generated tests) and novel circle recognition (14 generated tests), each after two authoring attempts. Both real artifacts also passed isolated Chrome preview checks using synthetic camera landmarks. Physical webcam/hand movement and resident suitability have not been tested. See [GENERATION-EVIDENCE.md](GENERATION-EVIDENCE.md) for artifact IDs and the distinction between real execution and earlier fixture checks.

When isolation is missing, the historical host compiler still provides draft-only diagnostics using in-memory files and trusted standard libraries. It does not execute modules, but pathological types/compiler vulnerabilities can still consume backend resources; it is not a hostile-upload service.

The prior assessment and generation evidence describe the earlier static-only milestone. This document describes the subsequent implementation. Existing static proposals without scene manifests must be regenerated.

## Developer setup

1. Install Docker Desktop using its official Windows instructions, enable the WSL2 Linux engine, and complete any required reboot. Installing WSL/Desktop is a system prerequisite, not something the app installs automatically.
2. On Windows, CarePlay checks `%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin\docker.exe` and `%ProgramFiles%\Docker\Docker\resources\bin\docker.exe`, then falls back to PATH. The child CLI environment includes its own bin directory so the Desktop credential helper is found; user/machine PATH and credentials are unchanged. Confirm `docker info --format '{{.OSType}}'` prints `linux`. The adapter rejects TCP/remote Docker contexts. Use a local Unix socket or Windows named pipe.
3. From the repository root, build the developer-controlled image (the helper invokes the native `docker build --tag careplay-validator:1 ./sandbox` command without requiring a PATH edit):

   ```powershell
   npm run sandbox:build
   ```

4. Set `CAREPLAY_SANDBOX=docker`, `CAREPLAY_AI_PROVIDER=codex`, and `CAREPLAY_DEMO=false` in `.env`. Confirm `codex login status`; no API key is required with Codex sign-in. Restart `npm run dev`.
5. `GET /api/status` and `/api/components` report the real daemon/image probe. Missing tools, a Windows engine, an unbuilt image or a rejected context leave execution disabled. No host-execution fallback exists.
6. Run `npm run validate:autonomous` for real model-authored Butterfly Garden and novel circle-to-bubble mechanics. This consumes Codex allowance, uses the real container, and fails unless independent semantic probes pass. The probes feed failures into the same three-attempt repair loop. It does not substitute fixture mechanics.
7. In the wizard, describe a new mechanic. A successful job opens the editor with the experimental artifact. Enable the camera and press Play. Try tracking loss, two residents, flower collisions and resident comfort. Save normally. Ask for an edit to fork the prior source/scene into a new build; the current version remains unchanged if validation fails. Undo restores the previous artifact reference.

The host needs Node, Chrome and Docker; the image owns its pinned TypeScript/esbuild dependencies. No generated package manifest or install command is accepted. Image creation deliberately needs network access; individual validation containers have none. The image tag pins explicit versions but not a base digest or transitive lockfile: audit/update and pin a reviewed digest before broader deployment. The image build and real isolated executions passed on this laptop. The limits below remain in force.

## Build boundary

`server/generation/docker.ts` copies only four fixed source/scene files plus a trusted acceptance selector into a fresh temporary directory. The workspace, user home, Codex credentials, `.env`, Docker socket and application secrets are not mounted or passed as container environment variables. Standard proxy variables are explicitly emptied to prevent Docker client proxy configuration from injecting credential-bearing URLs. The Docker client remains privileged trusted infrastructure; the application must never let generated code choose command arguments, mounts or image IDs.

The local Linux image ID is resolved before each job. The container runs as UID/GID 1000, with a read-only root, one read-only input mount, a 64 MiB noexec/nosuid temporary filesystem, no network, all capabilities dropped and no-new-privileges. Limits are 0.5 CPU, 256 MiB RAM with equal swap ceiling, 64 processes and 128 file descriptors. Docker's default seccomp profile still applies; no privileged mode or host namespaces are requested. Start/attach has a 45-second deadline and output cap; `docker rm --force` runs in cleanup even when the client times out. Cleanup failure can leave a stopped/running container; a developer must inspect Docker after daemon failures.

When Docker is configured, no host type-check is performed; compilation belongs inside the resource boundary. Inside the image, TypeScript checks the fixed contract, esbuild bundles source and tests, and a worker runs synchronous generated tests in a VM with per-call deadlines. Its heap target is 96 MiB and its overall deadline is 15 seconds. An independent smoke harness exercises setup, two hands, absent hands, bounded finite state and disposal over 100 steps. The VM/Node worker is defense in depth **inside Docker**, not a security boundary for the host. Generated tests can be wrong or adversarial; a passing test count is not proof of gameplay correctness. Dedicated developer-owned probes additionally exercise hand-following, flower collision, persistent blooming/departure, circle recognition, rejection of straight lines and tracking loss when the acceptance script is used.

Containers share the Linux VM kernel and rely on Docker Desktop, the daemon, host mount enforcement and compiler/build tools. Kernel/runtime vulnerabilities, compromised images/dependencies, side channels and denial of service remain possible. This is a local experimental facility, not a hardened hostile multi-tenant execution service. For stronger isolation use a dedicated disposable VM/runner account, no sensitive shared host mounts, audited images and an independently secured artifact service. Docker alone does not make arbitrary code safe.

## Browser boundary

### Shared runtime and complete-game validation (2026-11-09)

The reviewed `sandbox/runtime-core.mjs` and `runtime-api.d.ts` implement a data-only lifecycle SDK shared by the container and browser worker. Generated imports are restricted to `./contract`, `./mechanic` and `./runtime`. Rebuild with `npm run sandbox:build` after changing this SDK: the image records its SHA-256 label and the backend rejects an out-of-date SDK image. Restart the backend after changing imported server code. Building the trusted image requires network access for pinned dependencies; executing generated code has no network access.

Each synchronous generated test has a 1,000 ms budget, within the unchanged 15-second worker and 45-second container deadlines. Individual mechanic updates retain 100 ms limits. Once tests compile and reach execution, repairs retain their original source. Generic developer-owned design probes test supported matching/guiding interactions through every round, new arrangements, final completion, playable replay and wrong-target rejection where applicable. Custom interactions still require appropriate semantic probes; generic smoke checks alone do not establish their correctness.

The host supplies the authoritative design/lifecycle/accessibility manifest, maps approved artwork IDs to trusted SVGs, and renders plain-text labels and the objective/progress/round/replay UI. Generated snapshots carry finite data, never rendering code. Replay creates a fresh context with another seed; round restart increments the lifecycle revision. Legacy scenes without lifecycle metadata continue updating as before. New source hashes include design and SDK bytes; older immutable artifacts retain their original recorded hashes.

Component discovery uses developer-owned metadata and an allowlisted, reviewed external catalog. Phaser, PixiJS, Kenney Food Kit, Roseblox and Rosebud CLI are currently reference-only candidates, not executable adapters or downloaded dependencies. Recommendations do not authorize package installation, network access, asset purchases or component-library promotion. Arbitrary new artwork is unavailable: deterministic quality checks reject missing required art rather than relabelling an unrelated illustration. Visual checks are structural; `screenshotReviewed=false` is deliberate. See [upgrade evidence](DESIGN-UPGRADE-EVIDENCE.md).

Only a successful container report produces `artifact.json`, containing a scene manifest, provenance hashes and bundled JavaScript. The sibling proposal report records image identity and check results. Source, tests, contract and scene contribute to the source hash; bundle bytes have a separate SHA-256. The API validates artifact metadata and the bundle hash on read; the browser verifies them again against its saved configuration. Hashes detect accidental/mismatched edits; they are not signatures or protection against a compromised local backend or laptop owner.

Generated JavaScript is never imported into React, Vite or the trusted backend. It runs in a dedicated Worker created inside an `iframe sandbox="allow-scripts"` with **no allow-same-origin**, camera, microphone, geolocation, forms, popups, navigation or downloads. The iframe has an opaque origin. Its CSP denies network connections and external assets; inline trusted bootstrap and blob workers are the deliberate script exceptions. A transferred MessageChannel is accepted only from the parent and only once. The worker has no DOM. Its frame supervisor terminates it after a 500 ms update timeout (1.5 seconds for initial loading), unexpected extra replies or oversized serialized replies. The parent validates every snapshot before rendering.

The trusted app owns webcam/microphone permissions and renders local video behind the objects. It sends at most four mirrored, crop-adjusted palm centers, transient hand IDs, a timestamp and optionally a sound-trigger boolean. Stale tracking expires after 280 ms. No image, frame buffer, photo, audio samples, media stream, browser storage or credential is transferred. Hand IDs follow tracker ordering and can change when hands cross. Audio is a trusted, rate-limited gentle effect controlled by staff volume; generated code supplies no URLs or audio bytes.

Spawn outcomes are idempotent by entity ID in both preview and validator: a mechanic may create an entity and publish a spawn event without duplicating it. Duplicate IDs and invalid bounds fail validation, including during semantic replay. The parent accepts at most 64 finite entities, bounded identifiers/radii/positions and a completion boolean. It maps them to trusted SVG art; generated code cannot inject HTML, React components, styles or URLs. Blooming is a generic completion animation, honoring reduced motion. Unsupported rendering features/assets are intentionally unavailable. Manual movement pace, participant count and audio settings work; change object layouts, collision zones and rules through the assistant/rebuild rather than the trusted template controls.

Browser isolation is weaker than a separate OS VM. There is no enforceable per-worker browser heap quota; structured-clone allocations, message floods, CPU/memory exhaustion, browser bugs and timer throttling remain risks. A busy worker can degrade or crash the browser before the watchdog acts. CSP and opaque origins reduce access/exfiltration; they are not a guarantee against browser exploits. The preview is suitable for developer experimentation with review, not arbitrary public uploads.

## Quarantine and persistence

Reusable components now have a separate persistent quarantine under `.careplay/components`. Candidate/validated/approved are registry states, not permission for host execution. Exact version/hash references are revalidated inside Docker before linking into an isolated artifact. The trusted image permits only the enumerated pinned `./component-<hash>` modules; standalone modules cannot import other generated components. Source, tests and fixture/asset payloads remain separate from registry metadata. Local CLI developer promotion is independent from staff launch approval. See [component registry evidence, interfaces and residual risks](COMPONENT-REGISTRY-EVIDENCE.md).

Registered visuals use bounded declarative SVG primitives rendered by trusted React code. Arbitrary SVG/HTML/CSS, URLs and executable rendering callbacks remain prohibited. Snapshot visual state is limited to idle/selected/completed/disabled. This adds no generated DOM execution privilege.

Artifacts stay in ignored `.careplay/proposals/<uuid>/`, outside frontend imports and the shared registry. The browser saves immutable artifact references and scene metadata in its normal IndexedDB version history. Keep the backend proposal folder to reopen saved generated games; missing/damaged artifacts show an actionable error. Job polling links are session-local; saved artifact URLs survive backend restart. There is currently no artifact retention policy/export UI, signing service, distributed storage or automatic garbage collection.

Staff approval launches only that experimental version; it never registers source in the trusted component library. Developer promotion is a separate local CLI workflow requiring an exact version/hash and review reason; approved generated modules still run only in isolation. Execution success does not establish accessibility, clinical benefit or suitability for residents. Staff must review the actual game before launch.

API host/origin checks and loopback binding remain in place. This is not an authenticated production service; other local processes remain trusted. Do not expose the API/Vite proxy to a LAN or public internet.

## Verification scope

The [validation-gates audit](VALIDATION-GATES-AUDIT.md) separates nonblocking presentation suggestions from hard safety/playability gates. Sequential/pool spawning and delayed reveals are exercised through actual completion. New lifecycle manifests declare fixed versus shuffled layouts. Supported HTTP request metadata is capped at 1 MiB and decoded across UTF-8 chunk boundaries; prompt/schema/concurrency limits and container/browser boundaries remain in force.

`npm test` covers static validation/repair, preview gates, tracking expiry, command restrictions, output validation and original game logic. Playwright's isolated-preview and experimental-editor tests use **hand-authored trusted fixtures**, explicitly separated from live AI evidence. They cover opaque origin access, watchdog termination, data transport, create/play/edit/undo/save and existing workflows. `npm run validate:autonomous` is the distinct live model + real container + independent semantics check, and fails before spending model allowance when prerequisites are absent. The separate opt-in `CAREPLAY_TEST_ARTIFACTS=true npx playwright test tests/generated-artifacts.spec.ts` suite requires real successful semantic-validation artifacts and reads them from the local API without mocking generated code. It drives controlled landmarks through the mirror adapter to test following/bloom persistence and circle-to-bubble creation. It is automated synthetic-input evidence, not physical webcam validation.

Official boundary references: [Docker run restrictions](https://docs.docker.com/reference/cli/docker/container/run/), [iframe sandbox semantics](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox), [CSP sandbox caveats](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox). In particular, iframe sandboxing is an actual element attribute; CSP sandbox is not relied on through a meta tag.
